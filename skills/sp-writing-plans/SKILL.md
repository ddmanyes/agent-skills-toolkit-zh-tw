# 撰寫實作計畫
沿用使用者指定的計畫或專案現有位置；沒有慣例時使用 IMPLEMENTATION_PLAN.md。

計畫至少寫明目標、範圍、必要的檔案／模組、步驟依賴、預期行為與驗證方法。依可獨立驗收的成果分步，不固定每步分鐘數或每步提交。

- 先讀與本次決策直接相關的入口及規範；只有跨模組設計需要時才建立結構圖。
- 未確定的事項寫成有影響與解決方式的待確認項，不用沒有行動意義的佔位符，也不假稱所有細節已知。
- 使用者要求 test-first，或已批准 TDD 時，採每個行為一個 red → green → 必要的 refactor 切片。其他工作選用與風險相稱的現有檢查。
- 為每個切片標出真正的前置依賴；一般功能以可端到端驗證的窄切片交付，不機械地拆成全部資料層、全部 API、全部 UI。
- 廣泛改名、型別或 schema 遷移若無法逐切片保持可用，採 expand → migrate → contract：先保留新舊介面並存、分批遷移呼叫端、確認沒有舊使用者再移除。若仍需共同整合才能通過，明列整合驗證關卡，不宣稱各批都可獨立發布。
- 遠端 issue／ticket 的建立、修改與關閉依使用者授權；本機計畫不自動發布。
- 每項指明何時算完成及失敗後怎麼處理；在已授權範圍內修復並重跑受影響檢查。
- Commit／push 依原始授權及專案慣例安排，不用計畫自行擴張發布權限。

需要計畫審查時提交具體方案並等待；使用者已批准執行時接續完成工作。以繁體中文說明計畫與未決事項。
