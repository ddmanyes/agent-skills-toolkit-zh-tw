# 改善專案架構

先讀 [模組設計](../codebase-design/SKILL.md)。此技能提出候選與設計，實作依使用者已給的授權接續；不把報告當成自動重構的批准。缺少設計參考時，使用實際呼叫端、公開契約與測試作依據並說明限制。

## 探索範圍

使用者已指定模組或痛點時直接採用。否則查看近期提交與反覆修改的檔案，優先檢查變更熱點，再依證據擴大範圍。讀適用指示、專案指定詞彙表（`GLOSSARY.md` 或既有 `CONTEXT.md`）、ADR、呼叫端及測試。必要時依 glossary map 找到對應子領域；不強制遷移文件。

找出理解一個概念要跨多檔跳轉、同一行為修改分散、包裝沒有降低呼叫者負擔、依賴洩漏或無法透過介面驗證的具體例子。用 deletion test 檢查抽象是否承擔責任，保留權限、交易、錯誤語意。缺少測試不等於模組一定要合併。

## 呈現候選

每項列出檔案與位置、觸發情境、目前摩擦、擬議方向、前後示意、預期改善、遷移與回歸風險、推薦程度（Strong／Worth exploring／Speculative）。將可證實問題與設計偏好分開；沒有可靠候選就如實回報。

多模組候選預設產出單檔 HTML，比較前後關係，使用內嵌 CSS／SVG，不依賴 CDN；存入既有本機專案輸出位置或 `~/LocalWork/Codex/` 下本任務目錄。小範圍可在對話中列出；使用者指定 Markdown 時照辦。報告末尾推薦先處理哪項及原因。

候選若牴觸 ADR，引用決策並解釋為何值得重議。未選定方向時先呈現候選，再詢問影響設計的選擇；已有明確授權及選定方案時繼續，不重複問批准。

## 深化與交接

對選定項目釐清介面、不變式、錯誤、副作用、依賴與測試。只有未決取捨才使用 `sp-brainstorming`；已定案詞彙及有持久價值的決策依 `domain-modeling` 記錄。比較替代介面時使用模組設計參考。

交接包括選定方案、影響檔案、遷移順序、既有行為與驗證條件；實作請求接續 `sp-writing-plans`／`sp-executing-plans`。審查或候選報告本身不授權刪測試、改正式資料、commit 或 push。以繁體中文回報證據及未驗證事項。
