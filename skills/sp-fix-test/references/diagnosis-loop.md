# 證據迴圈

1. 先建立能捕捉使用者原始症狀的觀察方式：既有測試、CLI fixture、開發環境 HTTP、UI 操作、去識別化 trace replay 或隔離 harness。閱讀程式以建立重現是合理的；尚未重現的推論標為假設。
2. 實際跑一次並保存命令、輸入、版本、錯誤或差異。單純沒有 crash 不代表捕捉到 bug。間歇性問題記錄失敗次數／總次數、seed、條件與時間；只在已授權資源範圍內增加重複，不固定跑 100 或 1000 次。
3. 一次減少一個輸入或步驟，保留仍可觸發相同症狀的最小情境。效能問題先固定資料、環境與基準，再量測或 profile。
4. 有多個可能根因時列出可反證的候選，每項附預測與區分方式；依證據排序，每次改一個影響因素。用 breakpoint 或有唯一標記的日誌取代無差別記錄。
5. 修復前確認回歸案例能失敗；修復後同時跑精簡案例與原始場景，再跑受影響檢查。若測試接縫不能表現多呼叫端／時間順序等真實故障，明列覆蓋缺口，不拿淺層測試當保證。
6. 清除本次新增的暫時日誌與探針；保留失敗證據和獨特回歸案例。僅清理已確認由本任務建立且不再需要的檔案，保留使用者修改。

日誌與輸出遮蔽憑證、私人 payload 及識別資料。無法重現時列出已試方法和缺少條件，可繼續唯讀定位但不能宣稱已確認根因或修復。正式環境探針、外部資料傳送與付費呼叫需有對應授權。
